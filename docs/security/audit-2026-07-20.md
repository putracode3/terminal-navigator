# Security Audit — Terminal Navigator
> Audit date: 2026-07-20 · Report v1.3 · Auditor: security-auditor skill
> Scope: whole app — `src-tauri/` (Rust backend) + `src/` (Svelte frontend), Tauri IPC surface, encrypted local storage, dependency trees (Cargo.lock, package-lock.json)
> Method: code & config review, dependency audit (`cargo audit`, `npm audit`), safe reproduction (read-only checks, no destructive testing) — no production/remote environment exists, this *is* the author's own machine
> Context docs: `docs/prd-terminal-navigator.md` (FR-06/FR-07/FR-13), `docs/backend/architecture.md` + ADRs 0004/0005/0008/0009/0010, `docs/qa/test-plan.md`

## 1. Executive summary

This is a personal, single-user desktop app — there's no network attack surface and no other people's data to leak. The real question is: *if someone else got physical or local access to this machine while the app is running, or if a future bug ever let a script run inside the app's window, how bad could it get?* Today: not catastrophic, but worse than it needs to be. The encryption itself (the part protecting your project list) is solid. The gaps are all about the walls *around* that encryption: the app has no content-security policy at all, one command that opens a real shell doesn't actually check whether you've unlocked the app first, and the data file on disk isn't locked down to only your own user account. None of these are exploitable *today* without another bug first — but they're exactly the kind of gaps that turn a minor future bug into a serious one. All are cheap to fix.

**Findings:** 0 Critical · 0 High · 3 Medium · 4 Low (2 verified dependency-hygiene items + 1 verified UX/trust-boundary gap + 1 new dependency-hygiene item from this round)
**Status as of v1.2:** M1, M2, M3, L1 all fixed-verified · L2/L3 accepted, unchanged.
**v1.3 re-audit (this round — FR-13 Settings Panel + zoom/tab-cycling additions):** the new `settings_store` module, `change_password`, and the Settings UI were reviewed end-to-end. **No new Medium/High/Critical findings** — the new code follows the same patterns the earlier fixes established (lock-state gating where data is sensitive, atomic+permission-safe writes, no logging of secrets, server-side validation not client-trust). One new Low (L4, a fresh dependency advisory unrelated to this session's own code) was surfaced by re-running `cargo audit` today.
**Top priority now:** none open that need code changes — L2/L3/L4 remain intentionally deferred (see §5).

## 2. Attack surface inventory

**IPC commands (all local, invoked from the app's own webview via Tauri's `invoke()` — no network listener of any kind):**
| Command | Touches project store? | Lock-state gated? |
|---|---|---|
| `unlock` | writes | n/a — this *is* the unlock action |
| `list_projects`, `add_project`, `update_project`, `delete_project` | yes | ✅ yes |
| `open_terminal` | yes (looks up project by id) | ✅ yes |
| `split_pane` | **no** | **❌ no — see M1** |
| `write_terminal`, `resize_terminal`, `close_terminal` | no (operate on an already-open PTY session id) | n/a (see M1's note) |
| `export_config`, `import_config` | yes | ✅ yes (import re-unlocks explicitly) |
| `path_exists` | no | n/a — read-only, no side effect, deliberately minimal surface (already documented as such in-code) |
| `get_settings`, `save_settings` (FR-13, new) | no — separate unencrypted `settings_store`, never touches `state.store` | n/a by design (NFR-8: theme/keybindings/sidebar-position must render correctly even at the unlock screen) — verified the `Settings`/`SettingsDto` structs carry only `theme_preset: String`, `keybindings: HashMap<String,String>`, `sidebar_position` enum: no key material, password, or project data ever passes through this path |
| `change_master_password` (FR-13, new) | yes (mutates the store's in-memory key/salt + re-persists) | ✅ yes — `guard.as_mut().ok_or_else(AppError::locked)?`, same pattern as every other mutating command |

**Roles:** exactly one — "the app's owner". No multi-user, no role scoping, no remote accounts. The only real boundary is *locked* vs *unlocked* (has the master password been entered this session).

**Sensitive data map:**
| Data | Where it lives | Protection |
|---|---|---|
| Project list (paths, names, notes, setup commands) | `~/.local/share/com.dennysetiawisnugraha.terminal-navigator/projects.enc` | AES-256-GCM, key from Argon2id(master password) — see §7 for what was verified sound; see M3 for file-permission gap |
| Master password (current & new, during rotation) | Held in memory only (Svelte `$state` in `SettingsModal.svelte`'s form fields, and as plain `String` args on the Rust side of `change_master_password`) for the duration of the call | Not persisted to disk, not logged (verified — no `eprintln!`/`println!`/`console.log` anywhere on the password path, and `ProjectStoreError`'s `Display` impls never interpolate the password itself, only fixed strings like "current password is incorrect"); constant-time comparison (`subtle::ConstantTimeEq`) against the *derived key*, not the raw password, avoiding a timing side-channel on unlock/rotation |
| Non-sensitive settings (theme id, keybinding combos, sidebar side) (FR-13, new) | `~/.local/share/com.dennysetiawisnugraha.terminal-navigator/settings.json`, plaintext JSON, by design (NFR-8) | Not a secret — verified the file genuinely contains nothing beyond the three fields above; inherits the 0700 directory permission set for M3 (same directory as `projects.enc`), though the file itself isn't individually chmod'd 0600 the way `projects.enc` is (see L4 discussion — not raised as a finding, since there's nothing sensitive in it to protect) |
| PTY session output/input | Runtime-only, never persisted (ADR-0007) | n/a — nothing to leak after the process exits |
| Exported config file | Wherever the user chooses via the OS file picker | Byte-identical copy of the encrypted file — not a plaintext leak (verified, §7) |

**Non-IPC entry points:** the OS file picker (`tauri-plugin-dialog`) for export/import destinations, and project path selection (FR-02) — both delegate path choice to the OS dialog, not raw user-typed strings reaching a shell.

**Dependencies:** `src-tauri/Cargo.lock` (544 crates, up from 510 at v1.0) via `cargo audit`; `package-lock.json` (212 packages, unchanged) via `npm audit`. See §6.

## 3. Findings

### v1.3 re-audit — FR-13 Settings Panel, `change_password`, zoom/tab-cycling (2026-07-20)

No Medium/High/Critical findings. Specifically checked and cleared (evidence, not assertion):

- **`change_password` ordering/rollback** (`project_store/mod.rs:141-176`) — new salt/key derived into locals (`new_salt`/`new_key`) and only assigned to `self` after both succeed; on a `persist()` failure the previous key/salt are restored before returning the error. This closes exactly the ordering bug code-reviewer already caught pre-merge this session (deriving into locals first, not mutating `self` eagerly) — confirmed the fix is actually in the shipped code, not just described in a comment.
- **No secret logging** — grepped every password-touching path (`change_password`, the `change_master_password` command, `SettingsModal.svelte`'s form handlers) for `eprintln!`/`println!`/`console.log`/`dbg!`; none found. `AppError`'s `Display` messages for password-related errors are fixed strings ("current password is incorrect", "new password cannot be empty") — the password value itself is never interpolated into any error, log, or serialized response.
- **Keybinding-conflict validation is server-side, not client-trusted** — `settings_store::save()` calls `validate()` unconditionally before every write (`settings_store/mod.rs:87-105`), regardless of what the frontend sends via `save_settings`. A compromised or buggy frontend cannot bypass the duplicate-combo check by skipping its own client-side copy.
- **Atomic-write temp-file permissions (TOCTOU check)** — `project_store::persist()` calls `set_permissions(&tmp_path, 0o600)` **before** `std::fs::rename` (`project_store/mod.rs:192-205`), so the file is never briefly world-readable between creation and lock-down; permissions carry through the rename since it's on the same filesystem. `settings_store`'s equivalent `write_atomic` does not chmod its temp file, but since `settings.json` holds nothing sensitive (verified above) and lives inside the already-0700 data directory (set once in `lib.rs` before `AppState` is constructed, i.e. before either file is ever written), there's no reachable window where an unprivileged local user could list or open it anyway.
- **`change_master_password` IPC handler is lock-gated** — like every other mutating command (`commands/mod.rs:323-332`), consistent with the M1 fix pattern; no drift reintroduced.
- **No new XSS sinks** — grepped all Settings-related Svelte files (`ThemePresetCard`, `KeybindingRow`, `SegmentedControl`, `SettingsModal`, plus `TerminalPane`) for `{@html}`; zero matches. Theme preset colors are bound via Svelte's `style:` directive from a fixed, hardcoded 4-preset list in `theme-presets.ts` (never IPC- or user-supplied), so even a CSS-injection angle doesn't apply. M2's CSP fix remains intact and unaffected (`tauri.conf.json` still sets the explicit `csp` from the earlier fix).
- **No new dependencies of concern** — the only new Cargo dependency this session is `subtle = "2"` (RustCrypto, actively maintained, used correctly for constant-time key comparison — a net-positive addition, not a risk). No new npm dependencies were added for the Settings UI (built entirely from existing `Modal`/`Input`/`Button` components).

### L4 — `quick-xml` 0.39.4 (transitive, via Wayland clipboard support) — 2 high-severity advisories, build-time-only exposure
- **Severity:** Low (contextual — see impact) · **Status:** open (informational)
- **Category:** Dependency hygiene / A06:2021 (Vulnerable and Outdated Components)
- **Evidence:** `cargo audit` (re-run today as part of this round) reports RUSTSEC-2026-0194 (quadratic runtime parsing a start tag's attributes) and RUSTSEC-2026-0195 (unbounded namespace-declaration allocation → memory exhaustion), both rated 7.5/High upstream, against `quick-xml 0.39.4`. **Verified** the dependency path via `cargo tree -i quick-xml@0.39.4`: `terminal-navigator → tauri-plugin-clipboard-manager → arboard → wl-clipboard-rs → wayland-protocols-wlr → wayland-client → wayland-scanner` (a proc-macro crate). `wayland-scanner` parses Wayland protocol XML **at compile time**, from XML files bundled inside the `wayland-protocols`/`wayland-client` crates themselves — not from any runtime input, network data, or clipboard content. A second, already-patched `quick-xml 0.41.0` also exists in the tree (pulled in separately via `tauri-utils` → `plist`), so the fix is already partially propagated; only the Wayland-scanner path is still pinned to the vulnerable version via `wl-clipboard-rs`'s own dependency constraint.
- **Impact:** none at runtime. This crate never parses attacker-reachable data for this app — it only runs once, during `cargo build`, over static protocol-definition XML that ships inside the dependency itself. There is no path from "user does something in the app" to "this parser runs on untrusted input." This is why it's Low despite the 7.5 upstream rating: severity there assumes the classic case (a server parsing untrusted XML at runtime), which doesn't apply here.
- **Remediation:** no action needed now. Track for the next time `arboard`/`wl-clipboard-rs` publish a release pulling in `quick-xml >=0.41.0` (upstream fix already exists for the crate itself; this project just needs the dependency chain to catch up) — a `cargo update` at that point should resolve it with no code change on this project's side. **Size: none now, defer.**
- **Routes to:** accepted for now — revisit trigger in §5.

### M1 — `split_pane` can open a real shell without the app ever being unlocked
- **Severity:** Medium · **Status:** fixed-verified (2026-07-20) — `src-tauri/src/commands/mod.rs`, lock-state check added before spawning; regression coverage note added to `docs/qa/test-plan.md` §6 (full handler-level test deferred, see that entry for why); `cargo test` green (37 tests)
- **Category:** Authorization / A01:2021 (Broken Access Control) — cross-command consistency gap
- **Evidence:** `src-tauri/src/commands/mod.rs:156-171` — `split_pane` never touches `state.store` at all, unlike every other command that has side effects (`list_projects`, `add_project`, `open_terminal`, etc., all check `guard.as_ref()/.as_mut().ok_or_else(AppError::locked)?` — confirmed by reading every `#[tauri::command]` in the file). `split_pane` takes a raw `cwd: String` and calls `state.pty_manager.spawn(...)` directly. **Verified** by code reading — the omission is real and consistent (not a false positive from a different guard mechanism elsewhere).
- **Impact:** the app's own UI never exposes this while locked (the unlock screen has no split-pane control), so today this requires another bug to reach (see M2) — but architecturally, *spawning an actual shell process* is gated by nothing, while every *data* operation is gated by the master password. If any future code path (or a compromised dependency, or manual `invoke()` from a JS console in a dev build) calls `split_pane` before unlock, it runs a real shell on the user's machine with no password check at all. This is the specific command that turns "a script got to run inside the webview" into "that script has a shell".
- **Remediation:** add the same lock-state check used everywhere else. Since `split_pane` doesn't otherwise need project data, checking `guard.as_ref().ok_or_else(AppError::locked)?` before spawning is a one-line, non-breaking fix. **Size: code-fix (small).**
- **Routes to:** direct fix (backend-implementer pattern already established in the same file — no design decision needed).

### M2 — No Content-Security-Policy configured (`"csp": null`)
- **Severity:** Medium · **Status:** fixed-verified (2026-07-20). `src-tauri/tauri.conf.json` now sets `"csp": "default-src 'self'; connect-src ipc: http://ipc.localhost; style-src 'self' 'unsafe-inline'; font-src 'self'"` (the `connect-src ipc:`/`http://ipc.localhost` allowance follows Tauri v2's own documented CSP guidance for its internal IPC bridge). Rebuilt cleanly (`Terminal Navigator_0.1.0_amd64.deb`); author confirmed by hand that the app renders normally with no CSP-violation errors.
- **Category:** Configuration hardening / A05:2021 (Security Misconfiguration)
- **Evidence:** `src-tauri/tauri.conf.json:19-21` — `"security": { "csp": null }`. Tauri's own security guidance recommends setting a CSP specifically because it's the browser-level backstop between "a script somehow runs in the webview" and "that script can call `invoke()` and reach every IPC command". **Verified** by reading the config; cross-checked that there's currently no rendering sink for this to be exploited *today* (`grep` across all `.svelte` files for `{@html}` and `innerHTML`/`outerHTML` — zero matches, Svelte's default auto-escaping is intact everywhere).
- **Impact:** currently mitigated by there being no injection sink in the code today. But this is exactly the kind of gap that matters the day a future feature (or a compromised npm dependency) introduces one — with `csp: null`, there is no independent layer stopping an injected script from calling `invoke('split_pane', ...)`, `invoke('export_config', ...)`, etc. directly. Combined with M1, that's a straight line from "XSS" to "arbitrary shell process".
- **Remediation:** set an explicit, restrictive CSP in `tauri.conf.json`, e.g. `"csp": "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'"` (adjust `style-src` if any inline styles are needed — check after setting), then run the app and confirm nothing breaks (fonts/xterm.js rendering, in particular). **Size: config-fix (small, needs a manual smoke-test pass after).**
- **Routes to:** direct fix + manual verification (the qa-tester launch-environment charter in `docs/qa/test-plan.md` §5.1 is a reasonable place to add "app still works with the new CSP" as a one-time check).

### M3 — Encrypted data file and its directory use default (world-readable) permissions
- **Severity:** Medium · **Status:** fixed-verified (2026-07-20) — `src-tauri/src/lib.rs` (directory → 0700) and `src-tauri/src/project_store/mod.rs` (data file → 0600) both set explicit Unix permissions now. Regression test `project_store::tests::data_file_is_restricted_to_owner_only` added — confirmed failing before the fix (found 0644) and passing after
- **Category:** Configuration hardening / A01:2021-adjacent (Sensitive Data Exposure via filesystem)
- **Evidence:** `src-tauri/src/project_store/mod.rs:132` (`std::fs::write(&self.data_file, envelope)?`) and `src-tauri/src/lib.rs:26` (`std::fs::create_dir_all(&data_dir)`) — neither call sets explicit permissions. **Verified** on the live system: `ls -la ~/.local/share/com.dennysetiawisnugraha.terminal-navigator/` shows `projects.enc` at `-rw-r--r--` (0644, world-readable) and the containing directory at `drwxr-xr-x` (0755, world-listable). The file is only *not* reachable by other local users today because the parent `~/.local/share` itself happens to be `drwx------` (0700) on this particular system — a property the app doesn't set or guarantee, inherited from the user's own environment/distro defaults.
- **Impact:** on any system where `~/.local/share` (or an equivalent ancestor) isn't locked to owner-only — a different distro's defaults, a shared/multi-user machine, a container, a backup tool that preserves broader permissions — any other local user could copy out the ciphertext for unlimited offline password-cracking, with none of the app's own constraints applying (Argon2id's cost only slows down guesses *made against this file*; it does nothing once the file has been copied elsewhere). Relying on an ancestor directory's permissions the app doesn't control is fragile, not a guarantee.
- **Remediation:** after creating the data directory and after writing the data file, explicitly set `0700`/`0600` respectively on Unix via `std::os::unix::fs::PermissionsExt` (`std::fs::set_permissions`). Roughly:
  ```rust
  #[cfg(unix)]
  {
      use std::os::unix::fs::PermissionsExt;
      std::fs::set_permissions(&data_dir, std::fs::Permissions::from_mode(0o700))?;
      std::fs::set_permissions(&self.data_file, std::fs::Permissions::from_mode(0o600))?;
  }
  ```
  **Size: code-fix (small).** Windows/macOS aren't in scope today (architecture.md §9 risk 4 — untested platforms), so this can stay Unix-only for now.
- **Routes to:** direct fix.

### L1 — Import confirmation doesn't warn that setup commands will auto-execute
- **Severity:** Low · **Status:** fixed-verified (2026-07-20) — `src/lib/patterns/Sidebar.svelte`'s import dialog now includes the warning sentence; `Sidebar.test.ts` still green (13 tests)
- **Category:** Sensitive-action UX / trust boundary (not OWASP-mapped — this is a "the user should know what they're agreeing to" gap, not a technical vulnerability)
- **Evidence:** `src/lib/patterns/Sidebar.svelte:220-231` — the import confirmation dialog says data will be replaced ("This cannot be undone") but says nothing about `setup_commands` (FR-04) being automatically written to a real shell the next time each imported project's terminal is opened, with no per-command review. **Verified** by reading the dialog copy directly.
- **Impact:** FR-07's intended use is syncing the user's *own* config across their *own* devices via git/manual file transfer, so today's realistic risk is self-inflicted and low. But if an exported file is ever received from someone else, or downloaded from an untrusted source, importing it means agreeing to auto-run unknown shell commands with no visibility into what they are — and the dialog gives no hint of that.
- **Remediation:** add one sentence to the existing dialog, e.g. "Imported projects' setup commands will run automatically the next time their terminal opens." Cheap text change, no new logic needed. **Size: config/copy-fix (trivial).**

## 7. What was checked and found sound

- **Encryption:** AES-256-GCM with a fresh random nonce generated on every encrypt call (verified by a test asserting two encryptions of the same plaintext produce different ciphertext — correct nonce-reuse avoidance).
- **Key derivation:** Argon2id via the `argon2` crate's default parameters (19 MiB memory, 2 iterations, 1-lane parallelism) — meets OWASP's baseline recommendation for password-based key derivation.
- **No password-guessing oracle:** decryption failure is intentionally indistinguishable between "wrong password" and "corrupted/tampered ciphertext" (AES-GCM's authentication tag conflates both cases) — confirmed correct and *intentional* per the code's own comment, a genuinely good practice already in place.
- **No injection surface:** no relational database (nothing to SQL-inject); project paths are passed to the subprocess API as a `cwd` argument, never concatenated into a shell command string; `setup_commands` are written as raw PTY input, functionally identical to the user typing them at their own shell — not a privilege-crossing injection since no boundary is crossed (own data → own shell).
- **Authorization consistency:** every project-data-touching command correctly gates on lock state except the one gap in M1 — this is exactly the kind of cross-command drift a dedicated audit is meant to catch, and only one instance was found.
- **No XSS sink present:** zero `{@html}` or `innerHTML`/`outerHTML` usage anywhere in the Svelte codebase — Svelte's default text-escaping is intact everywhere today (this is *why* M2 is Medium rather than Critical — the gap is real but not currently reachable).
- **No secrets in the repo:** no API keys, tokens, or credentials found committed anywhere in `src-tauri/` or `src/`.
- **Export is not a plaintext leak:** `export_config` copies the already-encrypted file byte-for-byte — confirmed by reading `config_sync::export` and its test.
