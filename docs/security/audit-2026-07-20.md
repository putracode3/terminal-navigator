## 1. Executive summary

This is a personal, single-user desktop app — there's no network attack surface and no other people's data to leak. The real question is: *if someone else got physical or local access to this machine while the app is running, or if a future bug ever let a script run inside the app's window, how bad could it get?*

**Since the last round, the app's own security model changed on purpose:** ADR-0014 (2026-08-12) removed master-password encryption entirely — project data is now a plain file, protected only by OS file permissions, not encryption. This audit's job for that change isn't to flag it as a regression (it's a deliberate, documented product decision, not a bug) but to verify it was removed *cleanly* — no leftover code that still assumes a locked state, the file permissions that are now the *only* protection are still genuinely in place, and the new one-time migration path doesn't leak the legacy password. It checks out clean, with one small stale-comment finding (L5) that could mislead a future reader about what `not_ready` actually protects. The other new addition this round (FR-01's Home-directory auto-seeding) introduces no new attack surface — the seeded path comes entirely from the OS, never from user input.

Dependency audits both grew since last round — not from anything this project's own code did, but from upstream advisories published in the interim (a D-Bus-related unsoundness warning on the Rust side; several build/test-tooling-only advisories on the npm side). All are assessed below as unreachable at runtime for the shipped app, same reasoning already established for the prior round's accepted items.

## 2. Attack surface inventory

**IPC commands (all local, invoked from the app's own webview via Tauri's `invoke()` — no network listener of any kind).** As of ADR-0014, "gated" no longer means a security boundary — the `locked`/`unlock` state machine is gone. The column below is renamed accordingly: it now tracks whether a command null-checks that the project store has finished its one-time startup load, which is a correctness concern (don't panic on a `None`), not an authorization concern (there is exactly one role, see below, and it can reach everything by design).

| Command | Touches project store? | Store-loaded null-check? |
|---|---|---|
| `init_store`, `migrate_and_load` (ADR-0014, replace `unlock`) | write | n/a — these *are* the load action |
| `list_sidebar_entries`, `add_project`, `update_project`, `delete_project`, `merge_projects`, `move_project`, `reorder_folder`, `rename_folder` | yes | ✅ yes |
| `open_terminal` | yes (looks up project by id) | ✅ yes |
| `split_pane` | no | ✅ yes — see L5 (the check itself is correct and unchanged; its explanatory comment is stale, not its behavior) |
| `write_terminal`, `resize_terminal`, `close_terminal` | no (operate on an already-open PTY session id) | n/a — same as before, unaffected by ADR-0014 |
| `export_config` | reads the file path directly, not via `state.store` | n/a — correct as-is; the file path is resolved once at startup and is always valid, there's nothing for a null-check to protect |
| `import_config` (ADR-0014: password param removed) | yes | n/a by design — import must work and reset the store regardless of whatever state it was in before, so it doesn't gate on the prior state |
| `path_exists`, `get_git_branch` | no | n/a — read-only, no side effect. `get_git_branch` reviewed in depth in v1.7 (no subprocess — reads `.git/HEAD` directly; see L8) |
| `home_dir`, `open_home_terminal` (v1.15, launch fallback) | no (`open_home_terminal` reads only `AppState.home_dir`, resolved once at startup — **no path comes from the frontend**) | n/a — verified v1.7; no new caller-controlled path |
| `get_settings`, `save_settings` (FR-13) | no — separate `settings_store`, never touches `state.store` | n/a by design — must render correctly even before the project store has loaded (during the migration prompt, in particular) — verified the `Settings`/`SettingsDto` structs still carry only UI-preference fields, no key material or project data |
| ~~`change_master_password`~~ | — | **removed, ADR-0014** — no master password left to change |

**Roles:** exactly one — "the app's owner". No multi-user, no role scoping, no remote accounts. **Changed this round:** there is no longer a *locked* vs *unlocked* distinction either — every project-data command is reachable as soon as the store has finished its one-time startup load (milliseconds after launch), by design. This is the intended effect of ADR-0014, not a gap: the single role now has one trust boundary only — physical/local access to the machine itself — same boundary the executive summary above has always framed this app's real threat model around.

**Sensitive data map:**
| Data | Where it lives | Protection |
|---|---|---|

A rejected migration attempt provably doesn't touch the on-disk file (verified via the existing `migrate_from_legacy_rejects_wrong_password_without_touching_the_file` test). | PTY session output/input | Runtime-only, never persisted (ADR-0007) | n/a — nothing to leak after the process exits |

### L7 — Launch auto-open runs the setup commands of whatever entry is named "Home", with no user click
- **Severity:** Low · **Status:** fixed-verified (2026-09-24) · **Verified** (code path traced end to end)
- **Fix applied:** launch logic extracted to `src/lib/launch.ts`; a Home *entry* is now opened with `openPlainTerminal` (IPC `split_pane` — plain shell, no `command_runner`) instead of `openTerminal`; import dialog copy reworded (`SettingsModal.svelte`); PRD FR-01 v1.20 / architecture v1.19 / test-plan v1.18 updated in the same change-set. **Verification:** `launch.test.ts` — 3 of 6 tests failed against the old behavior (`openTerminal` was called for a Home entry carrying `curl … | sh`), all 6 pass after; `openTerminal` is asserted *not* called for top-level and folder-nested Home entries; suite 496 vitest / 100 cargo, clippy + svelte-check clean. Not exercised in a running app (the app was not launched against the live data file). Residual by design: opening Home deliberately ("Open in new tab") still runs its setup commands — the L1 import warning covers that path.
- **Category:** Trust boundary / A08:2021-adjacent (running code from an imported data file) — extends L1
- **Evidence:** `+page.svelte:48-56` `autoOpenHomeOnLaunch()` → `appStore.homeProject` (`app.svelte.ts:97`: `allProjects.find(p => p.name === "Home")` — first match anywhere, top level or inside a folder) → `handleOpenProject` (`+page.svelte:100`) → IPC `open_terminal` → `pty_manager::spawn_for_project` (`pty_manager/mod.rs:121-131`) → `command_runner::run_setup_commands`, which writes each `setup_commands` line into the new shell followed by `\n`. The Home *seed* has empty `setup_commands`, but nothing in the auto-open path checks that; it just opens whichever entry carries the name. This behavior shipped 2026-08-13 (`568e118`), after v1.6, so no earlier round covered it.
- **Impact:** L1's scenario, one click cheaper. `import_config` replaces the whole store with the imported file (validated for *shape* only — `config_sync::import` → `validate_plain_file`), so a config file from someone else can contain a project named "Home" with arbitrary `setup_commands`; those then run as the user **on the next app launch**, not when the user chooses to open that project. L1's dialog warning ("setup commands will run automatically the next time their terminal opens") still applies but reads as "when I open a project", not "when I start the app". Realistic exposure is small (FR-07 is meant for the author's own devices; the same file is already trusted for every other entry) — hence Low, not higher. Note v1.18's Delete protection is a *UX guard by name*, not a security control, and doesn't change this.
- **Remediation:** make the auto-open path not run setup commands — e.g. open it through a plain-shell path (the existing `open_home_terminal`/`split_pane`-style spawn at the entry's `path`) instead of `open_terminal`, or run setup commands only when the entry is the untouched seed (empty `setup_commands`). Also reword the import dialog to say "…when their terminal opens, including a "Home" entry at app launch". **Size: code-fix (small) + PRD FR-01 amendment.**
- **Routes to:** backend-implementer (+ PRD update in the same change-set per CLAUDE.md); UI copy tweak alongside.

### L8 — `get_git_branch` reads `.git`/`HEAD` with no size or file-type bound, on a synchronous command
- **Severity:** Low · **Status:** open · **Suspected** (read-path verified; hang not reproduced — see confirming step)
- **Category:** Robustness / local DoS (A05-adjacent)
- **Evidence:** `git_status.rs:22` (`fs::read_to_string(&candidate)` for a `.git` *file*) and `:37` (`fs::read_to_string(git_dir.join("HEAD"))`); handler is a plain `pub fn` at `commands/mod.rs:470`. Tauri v2 runs non-`async` commands on the main thread unless marked `#[tauri::command(async)]` (Tauri docs; not re-verified in source this round). A directory whose `.git/HEAD` is a FIFO or a symlink to something endless (`/dev/zero`) would block or exhaust memory in that call. Git itself can't ship such a `.git` inside a repo, so this needs a directory obtained another way (archive, shared folder) and added as a project or opened in a pane.
- **Impact:** at worst the app's UI freezes/crashes on a crafted directory — self-inflicted denial of service, nothing read out (the function only ever returns a branch name or a 7-hex hash, so no file content leaks). The `gitdir:` redirect can also point the read at any path named `HEAD`, still without disclosure for the same reason.
- **Confirming step (safe):** in a scratch dir, `mkdir .git && mkfifo .git/HEAD`, add it as a project, open a pane — if the window stops responding, confirmed.
- **Remediation:** check `metadata().is_file()` and read at most a few hundred bytes (`File::open(..).take(512)`); mark the command `#[tauri::command(async)]`. **Size: code-fix (trivial).** Cosmetic, same function: the branch string comes from untrusted file content and can contain control/bidi characters; it is rendered through Svelte text interpolation (`PaneTitle.svelte:50`, no `{@html}`), so it is not XSS, only a possible title-spoofing nuisance — optional to strip non-printables.
- **Routes to:** backend-implementer; qa-tester adds the special-file case to `git_status` tests.

### L9 — Capability set is broader than the app uses
- **Severity:** Low · **Status:** open · **Verified**
- **Category:** Configuration hardening / least privilege (A05:2021)
- **Evidence:** `src-tauri/capabilities/default.json:7-9` grants `opener:default`, `dialog:default`, `core:default`. `opener:default` (tauri-plugin-opener 2.5.4 `permissions/default.toml`) = `allow-open-url` + `allow-default-urls` (scope: `mailto:`, `tel:`, `http://`, `https://`) **+ `allow-reveal-item-in-dir`**. The frontend uses only `openUrl` (`TerminalPane.svelte:9`), and only for `http(s)` matches (see §7). `dialog:default` is used only for `open`/`save` (`Sidebar.svelte`, add-project form); message/ask/confirm dialogs are unused. Window permissions are already minimal (`allow-minimize`/`toggle-maximize`/`close`/`start-dragging`/`start-resize-dragging`) — fine.
- **Impact:** none today. This is the layer M2's CSP is a backstop for: if a script ever ran in the webview, `reveal_item_in_dir` and `mailto:`/`tel:` opens would be reachable for free.
- **Remediation:** replace `opener:default` with `opener:allow-open-url` plus a scope limited to `https://*`/`http://*`; replace `dialog:default` with `dialog:allow-open` + `dialog:allow-save`. Smoke-test open-URL, add-project browse, export/import afterwards (same manual-verify pattern as M2). **Size: config-fix (small).**
- **Routes to:** direct fix + a line in the runbook §2 smoke steps.

### L10 — Release workflow: workflow-wide write token and mutable action references
- **Severity:** Low · **Status:** open · **Verified**
- **Category:** CI/supply-chain hygiene (A08:2021)
- **Evidence:** `.github/workflows/release.yml:12-13` sets `permissions: contents: write` for the *whole* workflow, including the test-only `pre-flight` job (which needs read). Actions are referenced by mutable tag/branch: `actions/checkout@v4`, `actions/setup-node@v4`, `dtolnay/rust-toolchain@stable` (a branch), `tauri-apps/tauri-action@v0` (`:20,22,26,58,60,64,75`). Checked and fine: trigger is tag-push only (no `pull_request_target`, no fork-controlled input), and no `${{ … }}` value from untrusted input is interpolated into a `run:` script. Installers are built **unsigned** (no signing secrets) — informational, expected for a personal tool.
- **Impact:** low — single-author repo. A compromised action tag would get a `contents: write` token (release assets only, this repo).
- **Remediation:** set top-level `permissions: contents: read`, and `contents: write` only on `build-and-release`; pin the four actions to commit SHAs (Dependabot or manual bump). **Size: config-fix (small).**
- **Routes to:** deployment-engineer (runbook §2/§3 note).

### v1.5 re-audit — ADR-0014 (master-password removal) + FR-01 Home-seeding (2026-08-12)

**Retirement note — what no longer applies, and why that's correct:** the pre-ADR-0014 rounds below (M1, M3, and the sensitive-data framing throughout) were written against a threat model where a *locked* app was a real security boundary worth protecting — hence M1 flagging `split_pane` as a gap because it could "spawn a shell without the app ever being unlocked." ADR-0014 removed that boundary on purpose (see §2's Roles note). M1 and M3's *code* is unaffected and still correct (the same null-check and the same file permissions are still in place, verified below) — what's retired is only the *security* framing of why they matter. Re-labeling them as historical here, rather than deleting them, keeps the audit trail honest about what was verified when and why the reasoning changed, per this skill's own principle that accepted/superseded findings get a recorded status, not silence.

Checked and verified this round (evidence, not assertion):

- **No leftover locked-state assumptions in code** — grepped the entire `src-tauri/src/` tree for `locked`/`AppError::locked`; the only hit is an unrelated comment in `lib.rs` about a directory "happening to be locked down" (permissions, not app state). `AppError::not_ready()` (the `locked()` replacement) is correctly re-documented in `error.rs` as startup-ordering null-safety, not a security gate — matches its actual current usage everywhere it's called.
- **File/directory permissions, live-verified** — `ls -la ~/.local/share/com.dennysetiawisnugraha.terminal-navigator/` on the author's own running instance: `projects.enc` is `-rw-------` (0600), the containing directory is `drwx------` (0700). Both match `project_store::persist()` (`src-tauri/src/project_store/mod.rs`) and `lib.rs`'s setup code exactly — the M3 fix is still doing its job, now as the data's *only* protection rather than one layer of two.
- **Legacy migration path doesn't leak the password** — `ProjectStore::migrate_from_legacy` (`project_store/mod.rs`) and `MigrationPrompt.svelte` both grepped for `println!`/`eprintln!`/`dbg!`/`console.log`: none found on the password path. `ProjectStoreError::WrongPassword`'s message is a fixed string. A rejected migration attempt is covered by an existing test (`migrate_from_legacy_rejects_wrong_password_without_touching_the_file`) proving the on-disk file is untouched on failure — same rigor the prior audit applied to the now-removed `change_password`.
- **`init_store`/`migrate_and_load` don't change reachability versus the old `unlock`** — traced both for idempotency/misuse: calling `init_store` more than once just re-reads the (by-then-plain) file each time, no side effects beyond that; calling `migrate_and_load` against an already-plain file fails harmlessly (the plain file's leading bytes get mis-parsed as a salt/nonce, decryption fails, `WrongPassword` is returned, nothing is written — `persist()` is never reached on that path). No new way to read or corrupt project data that wasn't already possible before.
- **FR-01 Home-seeding introduces no new input-handling surface** — traced `project_store::load`'s seeding branch (`src-tauri/src/project_store/mod.rs`): the seeded path comes exclusively from Tauri's `path().home_dir()` (OS-resolved, never user-typed or IPC-supplied), `setup_commands`/`notes` are hardcoded empty, and the seeding branch bypasses `validate_input` entirely by construction rather than by omission (there's nothing for that validation to catch — name is a fixed literal, path existence is already checked by the `.filter(|p| p.exists())` right before). Once seeded, the entry is an ordinary `Project` with no special privilege — same as the M1/M3 retirement note above, this app's whole design already treats "open a shell at any listed project's path" as within the single-role trust boundary, so adding one more entry (auto-populated, not attacker-influenced) doesn't cross anything new.
- **CSP and XSS posture unchanged and still sound** — `tauri.conf.json`'s explicit CSP from the M2 fix is still in place verbatim; re-grepped all `.svelte` files for `{@html}`/`innerHTML`/`outerHTML` — still zero matches.

### L5 — Stale security-context comment on `split_pane`'s null-check
- **Severity:** Low · **Status:** fixed-verified (2026-08-12) — comment updated in `src-tauri/src/commands/mod.rs` to match `error.rs`'s current framing; `cargo check` clean, no behavior changed (comment-only)
- **Category:** Documentation/context drift (not itself exploitable — but the exact class of "left half-removed" issue this re-audit was specifically asked to check for)
- **Evidence:** `src-tauri/src/commands/mod.rs:395-398` — the comment above `split_pane`'s `state.store.lock().unwrap().as_ref().ok_or_else(AppError::not_ready)?` check still reads: *"Security audit 2026-07-20, M1: ... without this check it was the one command that could spawn a real shell before the app was ever unlocked — every other stateful command already gates on this."* This framing (unlock as a security boundary) is exactly what ADR-0014 retired — `AppError::not_ready()`'s own doc comment in `error.rs` correctly says this check is "not a security gate," but `split_pane`'s comment was carried over verbatim during the `locked()` → `not_ready()` rename and still tells the opposite story.
- **Impact:** none today — the check itself is correct and the behavior is unchanged (this is purely a comment, no logic reads it). The risk is entirely in what it could cause *later*: a future contributor (human or AI agent) reading this comment in isolation could reasonably conclude `not_ready` still gates something security-sensitive here, and either resist removing it when it's genuinely no longer needed, or — worse — treat its absence elsewhere as a real gap the way M1 originally was, misapplying a retired threat model to new code.
- **Remediation:** update the comment to match `error.rs`'s current framing, e.g.: *"Not a security gate (ADR-0014) — `split_pane` doesn't otherwise touch `state.store`, so this is purely defensive null-safety against being called before `init_store` has run, same as every other command's check."* **Size: comment-only (trivial).**
- **Routes to:** direct fix — applied same-round (see Status above), following this project's own established pattern of fixing trivial findings within the same audit session and recording both the "found" and "fixed-verified" states explicitly rather than silently.

### M1 — `split_pane` can open a real shell without the app ever being unlocked
- **Severity:** Medium · **Status:** fixed-verified (2026-07-20) — `src-tauri/src/commands/mod.rs`, lock-state check added before spawning; regression coverage note added to `docs/qa/test-plan.md` §6 (full handler-level test deferred, see that entry for why); `cargo test` green (37 tests)
- **Category:** Authorization / A01:2021 (Broken Access Control) — cross-command consistency gap

### M2 — No Content-Security-Policy configured (`"csp": null`)
- **Severity:** Medium · **Status:** fixed-verified (2026-07-20). `src-tauri/tauri.conf.json` now sets `"csp": "default-src 'self'; connect-src ipc: http://ipc.localhost; style-src 'self' 'unsafe-inline'; font-src 'self'"` (the `connect-src ipc:`/`http://ipc.localhost` allowance follows Tauri v2's own documented CSP guidance for its internal IPC bridge). Rebuilt cleanly (`Terminal Navigator_0.1.0_amd64.deb`); author confirmed by hand that the app renders normally with no CSP-violation errors.
- **Category:** Configuration hardening / A05:2021 (Security Misconfiguration)
- **Evidence:** `src-tauri/tauri.conf.json:19-21` — `"security": { "csp": null }`. Tauri's own security guidance recommends setting a CSP specifically because it's the browser-level backstop between "a script somehow runs in the webview" and "that script can call `invoke()` and reach every IPC command". **Verified** by reading the config; cross-checked that there's currently no rendering sink for this to be exploited *today* (`grep` across all `.svelte` files for `{@html}` and `innerHTML`/`outerHTML` — zero matches, Svelte's default auto-escaping is intact everywhere).
- **Impact:** currently mitigated by there being no injection sink in the code today. - **Routes to:** direct fix + manual verification (the qa-tester launch-environment charter in `docs/qa/test-plan.md` §5.1 is a reasonable place to add "app still works with the new CSP" as a one-time check).

### M3 — Encrypted data file and its directory use default (world-readable) permissions
- **Severity:** Medium · **Status:** fixed-verified (2026-07-20) — `src-tauri/src/lib.rs` (directory → 0700) and `src-tauri/src/project_store/mod.rs` (data file → 0600) both set explicit Unix permissions now. Regression test `project_store::tests::data_file_is_restricted_to_owner_only` added — confirmed failing before the fix (found 0644) and passing after
- **Category:** Configuration hardening / A01:2021-adjacent (Sensitive Data Exposure via filesystem)
- **Evidence:** `src-tauri/src/project_store/mod.rs:132` (`std::fs::write(&self.data_file, envelope)?`) and `src-tauri/src/lib.rs:26` (`std::fs::create_dir_all(&data_dir)`) — neither call sets explicit permissions. **Verified** on the live system: `ls -la ~/.local/share/com.dennysetiawisnugraha.terminal-navigator/` shows `projects.enc` at `-rw-r--r--` (0644, world-readable) and the containing directory at `drwxr-xr-x` (0755, world-listable). The file is only *not* reachable by other local users today because the parent `~/.local/share` itself happens to be `drwx------` (0700) on this particular system — a property the app doesn't set or guarantee, inherited from the user's own environment/distro defaults.
- **Impact:** on any system where `~/.local/share` (or an equivalent ancestor) isn't locked to owner-only — a different distro's defaults, a shared/multi-user machine, a container, a backup tool that preserves broader permissions — any other local user could copy out the ciphertext for unlimited offline password-cracking, with none of the app's own constraints applying (Argon2id's cost only slows down guesses *made against this file*; it does nothing once the file has been copied elsewhere). Relying on an ancestor directory's permissions the app doesn't control is fragile, not a guarantee.
- **Remediation:** after creating the data directory and after writing the data file, explicitly set `0700`/`0600` respectively on Unix via `std::os::unix::fs::PermissionsExt` (`std::fs::set_permissions`). Roughly:
  ```rust
  #[cfg(unix)]
  {
      use std::os::unix::fs::PermissionsExt;
      std::fs::set_permissions(&data_dir, std::fs::Permissions::from_mode(0o700))?;
      std::fs::set_permissions(&self.data_file, std::fs::Permissions::from_mode(0o600))?;
  }
  ```
  **Size: code-fix (small).** Windows/macOS aren't in scope today (architecture.md §9 risk 4 — untested platforms), so this can stay Unix-only for now.
- **Routes to:** direct fix.

*New in v1.7 — checked and found sound (evidence):*
- **FR-16 URL handling.** The link matcher in `@xterm/addon-web-links` 0.12.0 is `/(https?|HTTPS?):[/]{2}[^\s"'!*(){}|\\^<>`]*…/` — only `http(s)://` text can become a link, so a `file:`, `javascript:` or option-like (`-…`) string from terminal output never reaches `openUrl`. Activation requires Ctrl+left-click (`TerminalPane.svelte:105-108`); a bare click can't open anything. The opener plugin then enforces its own scope (`mailto:`/`tel:`/`http(s)://` only). The opened string is the exact visible text, not a hidden target.
- **OSC 8 hyperlinks (a terminal program can hide a URL behind other text).** xterm.js 6.0.0's default OSC 8 provider drops any non-http(s) URI (`allowNonHttpProtocols` unset → `["http:","https:"]` allow-list), asks `confirm()` first, and then calls `window.open()`; the app registers no `on_new_window` handler, and wry only wires the WebKitGTK `create` signal when one exists — so `window.open()` returns null and xterm logs "blocked". Verified by reading xterm/wry sources; **not exercised end-to-end**. Fragility to remember: adding an `on_new_window` handler later would change this — re-check then.
- **FR-17 has no command-execution surface.** `git_status.rs` never spawns `git` (`grep` for `Command::new`/`process::Command` across `src-tauri/src` → zero hits), so hooks, `core.fsmonitor`, `core.sshCommand` and repo-config-driven execution are not applicable. Only `HEAD` is read; only a `refs/heads/…` name or a 7-hex prefix is ever returned.
- **Home self-heal (`ensure_home_entry`, v1.19).** The path comes from `AppState.home_dir` (OS-resolved at startup), never from IPC or the data file; the healed entry has empty `setup_commands`/`notes`; persistence goes through the same `persist()` (0600, atomic). A failed persist is non-fatal and only prints the IO error text. `import_config`'s file check bounds-checks before indexing (`is_plain_format` requires `len > marker`) and decodes with `bincode` before replacing local data; not fuzzed this round. Home *protection* (v1.18) is by name and is a UX guard, not a security boundary — stated so nobody leans on it as one.
- **FR-08 drag/keyboard move** adds no IPC (handler list diff vs `6074098` = `home_dir`, `open_home_terminal` only; both reviewed above) — pane relocation is pure frontend tree manipulation.
- **CSP and window config unchanged and intact** (`csp` string byte-identical to the M2 fix; `withGlobalTauri`, `assetProtocol` and `devtools` not enabled; `transparent`/`decorations: false` add no permission — the four window permissions in `capabilities/default.json` are exactly what the in-app title bar needs). No `{@html}`/`innerHTML`/`outerHTML`/`insertAdjacentHTML`/`eval`/`new Function`/`document.write` anywhere in `src/` (re-grepped). The one `unsafe` block in `src-tauri/src` is a `#[cfg(test)]` `set_var` in a test.
- **Live file permissions (read-only `ls -l`, app not launched):** data directory `drwx------`, `projects.enc` `-rw-------`. `settings.json` is `-rw-r--r--` inside the 0700 directory (unchanged from prior rounds; holds only UI preferences).
