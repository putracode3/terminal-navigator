# Test Plan — Terminal Navigator
> Version 1.24 · 2026-09-25 · Mode context: verified defect recorded — early PTY output is dropped — see §6
> Runner: `cargo test` (Rust, src-tauri) · Vitest (frontend, src) · CI: none yet (personal project, manual builds — see docs/ops/runbook.md §2 for the pre-flight gate that stands in for CI today)
> Oracles: docs/prd-terminal-navigator.md (FR acceptance criteria) · docs/backend/architecture.md §9 (documented risks) · current behavior where neither specifies

This is a personal, single-developer desktop tool (not a team project, not commercial software) — scope and rigor below are sized to that reality. The headline gap this plan exists to close: a real bug (garbled terminal input, fixed in commit `ec19eff`) reached daily use before being caught, because its trigger — *how the app is launched* — is a dimension unit tests structurally cannot exercise. §5's charter is the direct answer to that.

## 2. Suite layout & conventions

- **Rust:** `#[cfg(test)] mod tests` inline at the bottom of each module (`pty_manager/mod.rs`, `command_runner/mod.rs`, `crypto/mod.rs`, `project_store/mod.rs`, `config_sync/mod.rs`, `commands/mod.rs`). Run: `cd src-tauri && cargo test`.
- **Frontend:** `*.test.ts` co-located next to the file under test (e.g. `TerminalPane.svelte` + `TerminalPane.test.ts`). Run: `npx vitest run` (single run) or `npx vitest` (watch). Type-check separately: `npm run check`.
- **Naming:** Rust tests read as specifications (`spawned_shell_always_sees_term_xterm_256color_regardless_of_this_processs_own_env`); Vitest `describe`/`it` blocks name the regression they protect against, not just the mechanism (e.g. `"TerminalPane — keystroke write ordering (regression: typed characters arrived at the PTY out of order...)"`) — keep following this pattern, it's what made this session's fixes traceable.
- **Fakes:** real PTYs are spawned in Rust tests (via `portable-pty` against `/bin/sh`/`$SHELL` in a tempdir) rather than mocked — deliberate, since the PTY/shell boundary is exactly where past bugs lived; jsdom-side, `@xterm/xterm`, `@tauri-apps/api/event`, and `$lib/api` are mocked (there's no real webview/IPC available under Vitest) — `resizeTerminal`/`writeTerminal` mocks must resolve a Promise (not just be a bare `vi.fn()`), since `TerminalPane.svelte`'s write-queue chains on them.
- **Cross-boundary contracts get a test on the boundary itself, not on one side of it.** A frontend test that asserts what the frontend *sends* (against its own mocked `$lib/api`) proves nothing about whether Rust can deserialize it — the two sides can drift freely with a green suite. The FR-11 `folderId`/`folder_id` bug (2026-07-23) lived in exactly that blind spot: `src/lib/api/index.test.ts` asserted the payload shape and passed, while every project-into-folder drop failed at runtime. So: for any IPC payload with a **nested** structure (a struct inside a struct, a tagged enum with fields), add a Rust test that deserializes the literal JSON string the frontend emits (`commands::tests::move_destination_deserializes_the_frontend_folder_payload` is the template). Tauri camel→snake-cases top-level command arguments only; nothing bridges nested field names, and serde's `rename_all` on an enum renames variants, not a struct variant's fields.

- **No CI wired yet** — `docs/ops/runbook.md` §2's pre-flight gate (`cargo test && npx vitest run && npm run check`, all must be green) is run manually before every build. If this project ever gets a public git remote, wiring that gate into GitHub Actions is the natural next step (noted in the runbook's §9 deferred list too).

## 5. Manual test charters

### 5.1 Launch-environment charter (primary — the gap that let `ec19eff` reach daily use)

**Goal:** catch bugs that depend on *how the OS process was started*, not on the app's code paths — these produce a different process environment (env vars, session type, cgroup) that unit tests, which always run inside a developer's own terminal-launched shell, cannot reproduce.

**Why this is a real, recurring risk, not a one-off:** the TERM-unset bug is the textbook case, but the same *class* of gap could resurface via other env-dependent behavior (locale/`LANG` affecting text width or wide-character handling, `DISPLAY`/`WAYLAND_DISPLAY` differing between X11 and native Wayland launches, `XDG_*` paths resolving differently). Treat this charter as standing, not a one-time check for this specific bug. **2026-07-22 addendum:** the risk isn't limited to OS process-launch environment — *build type* is the same class of gap. `npm run tauri dev` (Vite dev server, esbuild dependency pre-bundling) and `npm run tauri build` (Vite production build, esbuild minification) are different code paths that can silently diverge, and a developer's own testing loop is almost always `tauri dev` — see the new §5.1a below and step 5 added to the smoke sequence.

**Scope — for each launch method below, run this 2-minute smoke sequence:**
1. Launch the app.
2. Confirm the app opens straight to the project list (v1.13 — no unlock step, ADR-0014; the only exception is a one-time migration prompt on a machine whose data file predates ADR-0014, not a repeatable per-launch check), open any project's terminal.
3. Type a single letter, press Backspace, type another letter. **Pass:** display exactly matches what was typed, no duplicated/overlapping characters, no phantom spaces. **Fail signature:** see commit `ec19eff`'s description for exactly what this looked like.
4. Open a second project tab, split a pane, close a pane.
5. **(added 2026-07-22)** Run a full-screen TUI program (`vim` is universally available; any program that queries terminal capabilities on startup works) inside a pane. **Pass:** the program's UI renders (not blank) and keystrokes are reflected. **Also check (added 2026-09-25):** the TUI's painted area reaches the pane's right edge — the gap on the right should look like the gap on the left (a few pixels), not a wide strip of the pane's own colour. (Since design v3.4 the pane has a 4px inset on the normal screen and none on the alternate screen: the TUI's painted area should touch the pane border on the left and top, with only a sub-cell remainder of 0–7.8px on the right and 0–17px at the bottom; after quitting the TUI the prompt should sit 4px in from the border again. Two split panes of equal width must show the same column count. Real-app figures, isolated instance: left/top/bottom 0, right 7px.) Any leftover gap *below* the last row is the sub-cell remainder of a character grid, not this bug. Then **quit the TUI** and confirm the shell prompt and the output above it are intact — entering/leaving the alternate screen changes the grid by 1–2 columns (a SIGWINCH plus a reflow of the normal buffer), which no automated test exercises against a real shell. **Fail signature:** pane goes blank and stops accepting input right after launch — see §5.1a below for why steps 1–4 alone cannot catch this class of bug (they never exercise a DECRQM "request mode" terminal-capability query, which almost every full-screen TUI sends at startup and plain character echo never does).
6. **(added 2026-07-29, v2.8/ADR-0013 — native window decorations replaced by the in-app Title Bar)** Drag the window by an empty area of the Title Bar (not a button/input) and confirm it moves; click every window-control button (minimize, maximize/restore, close) and confirm each actually changes window state; drag from each of the 4 edges and 4 corners and confirm the window resizes; double-click the Title Bar's empty space and confirm it toggles maximize/restore. **Fail signatures to watch for specifically:** the window doesn't move at all (drag region not reaching the compositor); a click meant for a button instead starts a window drag (drag region swallowing the button's own click — components.md's Title Bar Do/Don't flags this exact risk); resize handles do nothing, or fight with GTK's own edge-detection. **Why this can't be a unit test:** `data-tauri-drag-region` and `startResizeDragging()` are handled by wry/the window manager below the DOM — jsdom has no such layer, so the whole interaction is unexercised by `TitleBar.test.ts`/`WindowResizeHandles`' own coverage (which only proves the button click handlers fire, not that the drag/resize gesture itself reaches the OS). **Why this is launch/environment-dependent, not just "manual UI testing":** GTK client-side decorations (what `decorations: false` puts the app in charge of on Linux) are drawn differently by different desktop environments/window managers — a smoke pass on the author's own DE does not establish behavior on another one, the same class of gap CON-5/architecture.md risk #4 already accepts for Windows/macOS entirely.

#### 5.1b Step 6's first run — the drag bug it caught (2026-07-29)

**This charter did its job on its first execution**, and the lesson is *not* the one the charter itself predicted, which is worth recording.

**Symptom:** with `decorations: false`, dragging the Title Bar never moved the window (0px, restored or maximized). Double-clicking the same empty area *did* correctly toggle maximize.

**Root cause — a permission-config bug, not an environment/WM bug:** ADR-0013 deliberately withheld `core:window:allow-start-dragging`, reasoning that the declarative `data-tauri-drag-region` attribute is handled by wry at the webview level and therefore bypasses the command/permission pipeline. It does not. Tauri's injected `drag.js` resolves the region in JS and then invokes an ordinary IPC command (`plugin:window|start_dragging`); withholding the permission denies every drag. Fix: grant it (`src-tauri/capabilities/default.json`). See ADR-0013's "Correction" section.

**Why double-click masked it:** double-click dispatches `internal_toggle_maximize`, the single state-changing command already inside `core:window:default`. So the *same attribute* produced one working gesture and one dead one — the diagnostic signature for this failure.

**Lessons for this plan:**
1. **Step 6's framing was too narrow.** It anticipated only compositor/DE-level fail modes ("drag region not reaching the compositor") and asserted the whole interaction was un-automatable. Half of it *was* automatable: the permission contract the gesture depends on is plain JSON. That half is now pinned by `TitleBar.test.ts` → "Window chrome capabilities (ADR-0013)", which fails-before/passes-after. The gesture itself remains manual-only; the config it rides on no longer does.
2. **A partially-working feature is a misleading oracle.** Because double-click worked, the natural read was "the drag region works, the WM is at fault" — which sent the first investigation toward GTK/Wayland/tao and away from a one-line config error. When one gesture on a shared mechanism works and a sibling doesn't, suspect per-command gating before suspecting the shared layer.
3. **Automated-repro caveat for this bug class.** `xdotool`/XTEST cannot reliably perform a window move-drag: `begin_move_drag` opens an interactive grab that synthetic `mouseup` doesn't cleanly end, so geometry reads immediately after a synthetic drag are stale and under-report movement. Control-test against a known-good native window (e.g. `gnome-calculator`) before trusting any negative result, and compare positions **across separate invocations**, not within one.

#### 5.1a Build type: `tauri dev` vs. the actual shipped binary (new dimension, 2026-07-22)

**Goal:** catch behavior that only exists in the production-bundled frontend (`npm run tauri build`), never in the developer's own `tauri dev` loop.

**What happened:** a bug report ("TUI blank and unresponsive") reproduced consistently through a full rebuild + reinstall (`npm run tauri build -- --bundles deb`), but never through `npm run tauri dev`. Root cause: Vite's production build (esbuild minification, the default for `vite build`) corrupted `@xterm/xterm`'s `InputHandler.requestMode()` — verified correct, valid source when rebuilt with `minify: false` — into throwing `ReferenceError: Can't find variable: i` at runtime, every time `requestMode()` ran (i.e. on the DECRQM query almost every full-screen TUI sends at startup). `tauri dev` never hit it: Vite's dev server pre-bundles dependencies via esbuild in a materially different code path from `vite build`'s minification pass.

**Fix (final):** switched the production minifier from esbuild to **terser** (`build: { minify: "terser" }` + the `terser` devDependency, in `vite.config.js`). terser minifies the same method correctly (keeps the enum-var declaration esbuild wrongly dropped) and produces an identically-sized bundle (~512 KB, same as esbuild, vs ~812 KB unminified), so full minification / NFR-7 is preserved. An earlier stop-gap (commit `c10a2f5`) disabled minification entirely (`minify: false`, ~812 KB) — correct but at odds with NFR-7; superseded by the terser switch. See `vite.config.js`'s own comment for the full evidence trail (the exact esbuild miscompilation, the terser output, before/after builds, and the real-`.deb` TUI render). **Note on verification reach:** the render half was confirmed end-to-end in the actual built `.deb` (a full-screen TUI renders correctly — decisive proof `requestMode()` no longer throws, since a thrown exception corrupts the parser and blanks the pane); the *keystroke-injection* half could not be exercised in the sandbox (xterm.js's hidden textarea does not accept synthetic X input events under XWayland), but the "can't type" symptom is the same parser-corruption root cause and code path as the blank render, now proven healthy.

**Scope:** whenever frontend dependencies change (`package.json`/`package-lock.json` touching `@xterm/*` or other packages with non-trivial runtime behavior) or `vite.config.js`'s build options change, run smoke-sequence step 5 above against the actual `npm run tauri build -- --bundles deb` output (installed or run directly from `src-tauri/target/release/`), not just `tauri dev`. A green `tauri dev` session proves nothing about the shipped binary for this class of bug.

**Cadence:** on every dependency bump touching frontend runtime packages, and every release (folds into §2's existing release gate in `docs/ops/runbook.md` — add step 5 there too).

### 5.1b Library-option-is-inert charter (FR-15 terminal transparency, 2026-07-22)

**Why this exists:** FR-15 shipped with terminal panes still opaque while every other surface went translucent. The cause was not our code: `xterm.js` 6.0.0 **flattens a translucent theme `background` against black and paints the result opaque**, and its `allowTransparency` option — still declared in the public typings — is never read by the implementation. Every unit test passed, `npm run check` was clean, and the option's presence in the `.d.ts` made it look supported. This is the same bug *class* as ADR-0006's WebGL addon: **a library advertises a capability its implementation does not deliver, and nothing short of looking at pixels reveals it.**

**Charter:** whenever a visual behaviour depends on a third-party library option — transparency, blending, rendering mode, GPU path — do not accept the typings, the docs, or the absence of console errors as evidence that it works.

**Method (proven twice in this project):**
1. Render the thing over a **high-frequency backdrop** — `repeating-linear-gradient(90deg, #FFF 0 8px, #000 8px 16px)` works well.
2. Screenshot the real window (`import -window <id>`; see the app-window notes in §5.1).
3. Compare **pixel variance** on a row inside the effect against a row over the bare backdrop (`convert <png> -crop WxH+X+Y txt:-`, parse channels, take stdev).
4. A working effect shows the backdrop's variance (FR-15's fix: stdev 127.49). A broken one shows a flat fill (the bug: stdev **0.00**).
5. When the option is a boolean, render **two instances differing only in that option**. If both measure identically, the option is inert — that single comparison is what proved `allowTransparency` dead.

**Verdict rule:** an inert library option is an architectural finding, not a code bug. Record it (ADR or design.md) so the next session does not re-enable it hopefully.

### 5.2 WebGL renderer fallback — RESOLVED 2026-07-21, superseded by this charter

**Original goal:** confirm the `try/catch` around `WebglAddon` construction (`TerminalPane.svelte`) actually results in a usable (if less optimal) terminal when WebGL is unavailable — architecture.md §9 risk 2 flagged this as unverified.

**What actually happened (debugger session, bug report: any full-screen TUI CLI rendering blank in a pane):** this charter's premise — that the risk was *context-creation failing* — was wrong. Context creation always succeeded; the addon simply never painted anything, ever, regardless of content. The `try/catch` fallback never had a chance to trigger because nothing threw. Confirmed with a standalone `xterm.js`+`@xterm/addon-webgl` harness outside Tauri, using `gl.readPixels()` on the framebuffer (not just visual inspection or console-error absence) — see ADR-0006's "2026-07-21 revisit" section for the full evidence trail.

**Resolution:** `@xterm/addon-webgl` is no longer loaded at all (`TerminalPane.svelte`); xterm.js's default renderer is used app-wide. `TerminalPane.test.ts` has a regression test asserting only the fit addon is loaded.

**Residual manual charter (replaces the above):** if `@xterm/addon-webgl` is ever reintroduced (e.g. after an upstream fix), re-verify it with the `gl.readPixels()`-on-the-framebuffer method — not just "no console errors" or a glance at the screen, both of which this bug slipped past. A blank pane can look identical to an empty/just-cleared one at a glance.

**Cadence:** only if `@xterm/addon-webgl` is reintroduced.

## 6. Accepted gaps

**Open defect (reproduced 2026-09-25, not an accepted gap — fix pending): output a process prints in the first moments after its PTY is spawned is lost.** The backend emits `pty://output/<id>` events as soon as the shell/program writes, but the frontend's `listen()` for that session is registered asynchronously after the pane mounts, and Tauri events emitted before a listener exists are not queued. ## 7. Instructions for AI agents

1. **New backend features ship with tests** at the level shown in §3 — Rust: inline `#[cfg(test)] mod tests` using real PTYs/tempdirs where the boundary being tested is PTY/filesystem/crypto; Vitest: co-located `*.test.ts`, mocking only the Tauri IPC/xterm.js boundary, never the component's own logic.
2. **Never weaken the net**: don't delete/skip/loosen an existing test to get the suite green — fix the code, or if the test's premise is actually wrong, say so explicitly and update this doc's §3 row for it in the same change.
3. **Environment-dependent behavior is not "just a unit test problem"** — if a bug's trigger involves *how the process was launched* or *what's in its environment* (not just its inputs), add it to §5.1's charter, don't just chase it with more mocked unit tests that will pass regardless (this session's early debugging spent real time on exactly this mistake before finding the actual `TERM` cause).
4. **Determinism rules bind**: no `sleep()`-based synchronization (use fake timers / explicit promise resolution — see `TerminalPane.test.ts`'s pattern), no real network calls, real PTYs are fine (they're the boundary under test, not an external dependency to fake).
5. **Update §1 and §3 in the same change-set** as any tests you add or remove.
6. **Uncovered decisions**: mirror the closest existing area's pattern (e.g. a new backend module spawning a subprocess should follow `pty_manager`'s real-process-in-tempdir style, not introduce mocking).
